## I. Типографическая иерархия

### 1.1. Заголовки

| Уровень | Markdown | Назначение | Пример |
|---------|----------|------------|--------|
| H1 `#` | Единственный на документ | Название документа | `# Context Provenance Protocol` |
| H2 `##` | Крупные разделы | §I, §II и т. д. | `## I. Проблема` |
| H3 `###` | Подразделы | Технические секции | `### 1.1. Канонизация` |
| H4 `####` | Детальные пункты | Примеры, случаи | `#### Год 1 (2026): пилоты` |

**Правило Title Case:** английские заголовки — Title Case (`Why This Matters`).
**Правило Sentence case:** русские заголовки — только первая прописная (`Почему это важно`).
**Запрет:** не использовать H1 внутри файла после первой строки.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 1.2. Выделение текста

• **Жирный** (`**text**`) — ключевой термин при первом введении, важное число, критический вывод.
  ○ Лимит: **максимум 2–3 выделения на абзац**. Больше — обесценивает.
  ○ Нельзя: целые предложения жирным.

• *Курсив* (`*text*`) — спекулятивные значения (например, *$1,500*), иностранные слова, названия документов.

• `Моноширинный` (`` `code` ``) — идентификаторы кода, CID-хэши, CLI-команды, имена файлов.

• ~~Зачёркнутый~~ (`~~text~~`) — устаревшие подходы, явно отвергнутые варианты. Редко.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 1.3. Пунктуация и типографика

• Тире — em-dash (—), не двойной дефис (--).
• Кавычки в прозе — «ёлочки» для русского, "curly" для английского.
• Прямые кавычки (`"text"`) допустимы только внутри блоков кода.
• Многоточие — символ … (U+2026), не три точки `...` в прозе.
• Числа тысячами: $1,500 (с запятой), не $1500.
• Денежные суммы: `$` перед числом, курсив если спекулятивно.

## II. Callout-блоки

Все callout-блоки реализованы через Markdown blockquote `>` + опциональный кодовый блок.

### 2.1. Ключевой инсайт

```
> **Инсайт:** Текст ключевого утверждения, которое читатель должен запомнить.
> Не более 2–3 предложений. Должно стоять самостоятельно.
```

Пример:
> **Инсайт:** Канонизация контекста — это не оптимизация затрат. Это формирование training signal для следующего поколения моделей.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

```
> ⚠️ **Внимание:** Критическая информация, которую нельзя пропустить.
> Используется редко — не чаще одного раза на раздел.
```

## III. Словарь символов

### 3.1. Символы статуса

| Символ | Значение | Контекст |
|--------|----------|----------|
| ✅ | Выполнено / готово | Статус задач, реализованные функции |
| 🔘 | Запланировано / не начато | Roadmap items |
| 🟢 | Готово к работе / green light | Статус систем, CI/CD |
| 🟡 | В процессе / осторожно | Промежуточное состояние, риски |
| 🔴 | Заблокировано / критично | Блокеры, P0-проблемы |
| ⚠️ | Предупреждение | Важные замечания, edge cases |
| ❌ | Отклонено / неверно | Ошибки, неподходящие подходы |

**Правило экономии:** не более 3–4 emoji на раздел. Избыток обесценивает внимание.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 3.2. Символы навигации и акцента

| Символ | Значение | Контекст |
|--------|----------|----------|
| ▶ | Начать / перейти к | Режимы чтения, CTA |
| ► | Акцент на пункте списка | Важные буллиты |
| ◀ | Вернуться / ссылка назад | Навигация |
| ▲ | Рост / улучшение | Метрики, тренды |
| ▼ | Снижение / уменьшение | Метрики, экономия |
| → | Причинно-следственная связь | Формулы, логические цепочки |
| ─ | Горизонтальный разделитель | Внутри кодовых блоков |

### 3.3. Рейтинги и прогресс

**Рейтинги** — звёздами:

```
★★★★★  — обязателен к прочтению
★★★★☆  — важен для ключевых читателей
★★★☆☆  — для технического due diligence
★★☆☆☆  — справочный материал
★☆☆☆☆  — узкоспециализированный
```

**Прогресс-бары** — блоковыми символами:

```

```

## IV. Разделители и структурные элементы

### 4.1. Межсекционные разделители

**Тяжёлый разделитель** (между крупными разделами):
```
═══════════════════════════════════════════════════════════════════════════════
```

**Лёгкий разделитель** (между подразделами):
```
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
```

**Правило:** в одном файле — один тип тяжёлого разделителя. Не смешивать `═══` и `───`.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 4.2. Блочные рамки

Правило рамок: **только box-drawing символы** (`╭╮╰╯│─┌┐└┘├┤┬┴┼╔╗╚╝║═`).
Запрет: смешивать `-` с `─`, `|` с `│`.

| Стиль | Символы | Применение |
|-------|---------|------------|
| Простая | `┌┐└┘─│` | Информационные блоки, примеры |
| Двойная | `╔╗╚╝═║` | Важные результаты, key metrics |
| Скруглённая | `╭╮╰╯─│` | Визуально мягкие блоки, определения |

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 4.3. Списки

```
• Основной буллит — для большинства перечислений
  ○ Подпункт первого уровня — детали, уточнения
    · Подпункт второго уровня — крайне редко; если нужно, упростить структуру

► Акцентированный буллит — для 1–3 важнейших пунктов в разделе

1. Нумерованный список — когда порядок важен: шаги, приоритеты
   1.1. Подпункт нумерованного — для алгоритмов, процессов
```

## V. Таблицы

### 5.1. Правила форматирования

• Всегда включать строку-разделитель (`|---|---|`).
• Числовые столбцы — выравнивание по правому краю (`|---:|`).
• Текстовые столбцы — по левому краю (по умолчанию).
• Заголовки колонок — Title Case (английский) или Первая прописная (русский).
• Десятичные числа — выравнивать по точке внутри ячейки визуально.

### 5.2. Пример правильно оформленной таблицы

| Метрика | Без CPP | С CPP | Дельта |
|---------|--------:|------:|-------:|
| Стоимость 200K-токенного контекста (30×) | $18.00 | $5.40 | **−70%** |
| TTFT на cached prefix | 4.5 с | 0.8 с | **−82%** |
| Disk usage (13 worktrees) | 16 GB | 3.2 GB | **−80%** |
| Audit query «что AI видел» | 30 мин | 1 SQL | **>1000×** |

### 5.3. Что запрещено в таблицах

• Длинные прозаические фразы в ячейках (максимум ~60 символов).
• Смешение типов данных в одном столбце.
• Пустые ячейки без явного «—» или «N/A».

## VI. Кодовые блоки

### 6.1. Обязательный тег языка

Каждый кодовый блок должен иметь тег:

````markdown
```typescript
const cid = await canonicalize(context);
```
````

Допустимые теги: `typescript`, `python`, `bash`, `json`, `yaml`, `text`, `math`, `sql`.
Для псевдокода и иллюстраций — тег `text`.
Для ASCII-диаграмм — тег `text` или без тега (если встроено в текст).

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

### 6.2. Когда использовать блок кода vs. рамочный блок

| Ситуация | Инструмент |
|----------|------------|
| Реальный код на языке программирования | ` ```typescript ` |
| Псевдокод / алгоритм / формула | ` ```text ` |
| Архитектурная схема (ASCII art) | Рамочный блок `╔═╗` |
| Вывод команды / shell-сессия | ` ```bash ` |
| Конфигурационный файл | ` ```yaml ` или ` ```json ` |

## VII. Математическая нотация

### 7.1. Inline vs. блочная математика

• Inline: переменные и короткие формулы в тексте — курсив: *T = (S_in, A, S_out, R)*.
• Блочная: выделенные формулы — в `text`-блоке с отступами и пояснениями.

### 7.2. Пример блочной формулы

```text
CID = multihash(SHA-256, DAG-CBOR(canonical(data)))

где:
  canonical(data)  — детерминированное CBOR-представление
  SHA-256          — хэш-функция с 256-битным выходом
  multihash        — self-describing hash (CIDv1)
```

### 7.3. Обозначения

• Множества — заглавные латинские курсивом: *S*, *A*, *R*.
• Функции — строчные: *canonical(x)*, *hash(x)*.
• Индексы — нижним подчёркиванием: *S_in*, *S_out*.
• Суперскрипты — через `^`: *S^n*.

## VIII. Диаграммы и ASCII art

### 8.1. Принципы

• Каждая диаграмма должна иметь **подпись** под ней (курсив) или являться частью
  именованного кодового блока.
• Ширина диаграммы: не более 79 символов (совместимость с 80-символьными терминалами).
• Стрелки: `→` (вправо), `←` (влево), `↑` (вверх), `↓` (вниз), `↔` (двустороннее).
• Для ASCII-flow: `──►`, `◄──`, `──┬──`, `──┤`.

### 8.2. Пример правильной диаграммы

```text
┌─────────────┐    canonical()    ┌─────────────┐
│   Context   │ ────────────────► │  DAG-CBOR   │
│  (any form) │                   │   bytes     │
└─────────────┘                   └──────┬──────┘
                                         │ SHA-256
                                         ▼
                                   ┌─────────────┐
                                   │    CID      │
                                   │ (content ID)│
                                   └─────────────┘
```

*Рис. 1. Процесс канонизации: от произвольного контекста к детерминированному CID.*

## IX. Голос и тон

### 9.1. Языковые правила

• Первое лицо множественного числа: «мы», «наш», «мы строим» — не «я».
• Прямые утверждения: «даёт 30-70% экономии» — не «может потенциально предоставить».
• Спекулятивное помечать: «ожидаемый» / *expected* / курсивом.
• Термин CPP-специфики: «канонизация» / «канон» — не «стандартизация».

### 9.2. Запрещённые клише

❌ «в эпоху AI» / «в эпоху больших языковых моделей»
❌ «революционный подход»
❌ «next-generation solution»
❌ «disruptive technology»
❌ «seamless integration»
❌ «robust infrastructure»
❌ «cutting-edge»

### 9.3. Предпочтительные формулировки

✅ Конкретные числа вместо «значительной экономии»
✅ «первый публичный canonical encoding standard» вместо «революционный»
✅ «протокол» вместо «платформа» (более точно)
✅ «infrastructure layer» вместо «экосистема»

